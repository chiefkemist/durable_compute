* Durable Compute
JavaScript is a common execution target; Web Platform APIs provide a shared
interface across its runtimes. =fetch= connects browsers and servers, while the
same =Request=/=Response= model also reaches named, stateful actors. The important
shift is what the host can recover after a request—or an entire process—ends.

Consider a workflow that fetches input, calls an AI service, waits hours for human
approval, then publishes a result. Its lifetime exceeds any one HTTP request or
server process. JavaScript runtimes and Web APIs supply a familiar programming
model; durability lets that work outlive the execution that started it.[fn:workflows]

** Runtimes & Web Platform APIs
An engine executes JavaScript; a runtime adds I/O. The shared Web API core:
=fetch=, =Request=, =Response=, =Headers=, streams, =URL= and Web Crypto.

| Runtime | Typical environment | Web API support |
|---------+---------------------+-----------------|
| Browser | Client | Core + DOM |
| Node.js | Server / cloud VM | Core; HTTP server adapters |
| Deno | Server / cloud VM | Core; =Deno.serve= |
| Bun | Server / cloud VM | Core; =Bun.serve= |
| QuickJS | Embedded engine | Web APIs supplied by host |
| workerd | Cloudflare / self-hosted | Worker subset; =fetch= handler |
| celld | Self-hosted fleet | Workers-compatible subset |

Support varies by runtime/version; DOM, CORS, cookies and streaming are not uniform.
*Client:* =fetch(request) -> Promise<Response>=.
*Server:* =handler(Request) -> Response | Promise<Response>=; startup APIs differ.

This common boundary is where the pieces connect: a =fetch= call can sit inside a
durable workflow step, a =Request= can be routed to a named stateful object, and a
host can suspend a program while external work completes. The HTTP interface
stays familiar while the host adds persistence, scheduling and recovery—not
because Fetch itself is durable, but because durability can be built around it.

Deno's team announced one year of bug/security fixes in October 2026, then ending
its runtime development; Deno remains open source.

*** The same HTTP objects, different server adapters
These are shortened excerpts/adaptations of the samples, not complete deployment

Start a Bun server using the =basic_server= routes. The handler receives a Web
=Request= and returns a Web =Response=.[fn:basic-http]

#+begin_src typescript
Bun.serve({
  port: 3000,
  routes: {
    "/": () => new Response("Hello, world!"),
    "/health": () => Response.json({ status: "ok" }),
    "/api/echo": {
      POST: async (request: Request) =>
        Response.json({ received: await request.json() }),
    },
  },
  fetch: () => Response.json({ error: "Not found" }, { status: 404 }),
});
#+end_src

A client uses those same Web APIs. This adapts =basic_client='s fetch/check/decode
sequence to the local server; =Headers= and =AbortSignal= are Web APIs too.

#+begin_src typescript
const request = new Request("http://localhost:3000/health", {
  headers: new Headers({ accept: "application/json" }),
  signal: AbortSignal.timeout(5000),
});
const response = await fetch(request);
if (!response.ok) throw new Error(`HTTP ${response.status}`);
console.log(await response.json());
#+end_src

The richer =basic_app= shares =router.fetch= between Bun and Node. Bun accepts a
Fetch handler directly; Node uses an HTTP adapter. Routing/application logic need
not change with the listener.[fn:app-adapters]

#+begin_src typescript
import * as http from "node:http";
import { createRequestListener } from "remix/node-fetch-server";
import { router } from "./app/router.ts";

http.createServer(createRequestListener(router.fetch)).listen(44100);
// Bun alternative: Bun.serve({ port: 44100, fetch: (r) => router.fetch(r) });
#+end_src

** Durable execution
- *Workflows:* persist step results; after interruption, replay reuses completed
  steps and retries unfinished work. Make external effects idempotent.
- *dquickts:* snapshot the JS heap and suspended stack at safepoints; restore and
  resume in another process using the same engine build. Host I/O is separate.

The paired =basic_do_workflows= / =basic_celld_workflows= examples put an ordinary
=fetch= inside a durable step. Excerpt from =ReportBuilder.run(event, step)=:

#+begin_src typescript
const report = await step.do("fetch source", async () => {
  const response = await fetch(event.payload.url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const text = await response.text();
  return { lines: text.split("\n").length };
});
await step.sleep("cool down", 2);
await step.do("record", async () => ({ instance: event.instanceId, report }));
return report;
#+end_src

The saved result is data, not a live =Response= or socket. On replay, a completed
step returns that data without fetching again; an unfinished step can retry.
The sleep does not require the original process to remain alive.[fn:workflow-samples]

*** dquickts: save the running program, not just a step result
The QuickJS extension demonstrates a deeper form of interruption and resumption:
a host can pause JavaScript *even in the middle of a loop*, serialize the runtime
heap and suspended call stack, and write that snapshot to disk. Objects, closures,
local variables, pending promise jobs and the saved instruction position are part
of the recoverable execution state.[fn:snapshots]

The original host process can then exit. A new process loads the snapshot into a
compatible engine build and resumes the program at the saved instruction, rather
than rerunning the workflow to reconstruct its progress. This makes hibernation
and long waits possible without keeping the original process resident.

The connection to workflow I/O is equally important: =JS_SuspendCall()= can park a
host call, and =JS_ResumeWith()= can supply its result after restoring the runtime.
The project's example uses a fetch-like host function to illustrate this boundary;
it is not a built-in implementation of the standard Fetch API. The host still
owns external I/O and safe handling of repeated side effects.[fn:host-calls]

The C embedder's core API sequence is small. This excerpt assumes JS is already
suspended; native registration, disk I/O and error handling are omitted. Between
the write and read, the host can save the bytes, exit, and reload them in a new
process.[fn:snapshots]

#+begin_src c
uint8_t *bytes = JS_WriteSnapshot(ctx, &len, &host, NULL, 0, 0);
/* Persist bytes to disk; a later process reloads them into bytes. */
JS_ReadSnapshot(rt2, bytes, len, NULL, 0, &host, &restored, err, sizeof(err));
JSValue result = JS_Resume(restored.contexts[0]);
#+end_src

** Durable Objects
A named, single-threaded actor owns strongly consistent SQLite/KV storage.
Cloudflare layers distributed routing, storage, alarms and WebSocket hibernation
onto workerd's Web API model. =fetch= is the HTTP seam, *not* durability itself;
RPC is another entry point. Persisted state survives eviction; JS call stacks do not.

For workflow-like workloads, these are complementary building blocks: one object
can own a job or agent's state, persist progress, and schedule an alarm to continue
later. Cloudflare's WebSocket hibernation can keep clients connected while the
object is out of memory. This recovers an actor from stored state rather than
restoring its running stack as dquickts does.[fn:object-durability]

In =basic_do_cells=, a Worker forwards HTTP to a stable object identity. The
object handles =fetch= as before, but explicitly persists its counter instead of
relying on a process-local variable.[fn:cell-samples]

#+begin_src typescript
import { DurableObject } from "cloudflare:workers";
type Env = { COUNTER: DurableObjectNamespace<Counter> };

export class Counter extends DurableObject<Env> {
  async fetch(): Promise<Response> {
    const n = ((await this.ctx.storage.get<number>("n")) ?? 0) + 1;
    await this.ctx.storage.put("n", n);
    return Response.json({ n });
  }
}

export default {
  fetch(request: Request, env: Env) {
    const id = env.COUNTER.idFromName("demo");
    return env.COUNTER.get(id).fetch(request);
  },
};
#+end_src

Other samples attach more capabilities to this model. These are independent
handler excerpts—not one combined handler.[fn:actor-samples]

#+begin_src typescript
// basic_do_sql: query the object's private SQLite database.
const total = this.ctx.storage.sql
  .exec("SELECT coalesce(sum(cents), 0) AS cents FROM entries").one();

// basic_do_alarms: arrange a future alarm() invocation, even after eviction.
await this.ctx.storage.setAlarm(Date.now() + 5000);

// basic_do_rpc: call a named actor's method instead of sending HTTP.
const snapshot = await env.CART.getByName("demo").add("coffee");

// basic_do_websockets: accept a socket using the hibernation-aware API.
const pair = new WebSocketPair();
this.ctx.acceptWebSocket(pair[1], ["chat"]);
return new Response(null, { status: 101, webSocket: pair[0] });
#+end_src

** celld: provider-neutral deployment
celld brings the Workers/Durable Objects model to your infrastructure:
V8 + per-cell SQLite + a shared object-storage bucket; compatibility gaps apply.

Following the Deno team's move to Cloudflare, the announced plan is to merge
celld's distributed self-hosting code and ideas into workerd—not a completed integration.

=basic_celld_cells= uses a plain class with injected state rather than Cloudflare's
base class. The HTTP contract, stable-name routing and explicit durable writes
remain recognizably the same.[fn:cell-samples]

#+begin_src typescript
export class Counter {
  constructor(private state: DurableObjectState) {}

  async fetch(): Promise<Response> {
    const n = ((await this.state.storage.get<number>("n")) ?? 0) + 1;
    await this.state.storage.put("n", n);
    return Response.json({ n });
  }
}

export default {
  fetch(request: Request, env: { COUNTER: DurableObjectNamespace }) {
    return env.COUNTER.get(env.COUNTER.idFromName("demo")).fetch(request);
  },
};
#+end_src

Both samples declare the =COUNTER= binding and =Counter= SQLite-class migration
in =wrangler.jsonc=. The source model is portable; storage ownership, deployment
and operational guarantees still belong to the chosen platform.

** Languages that compile to JavaScript
*** A language choice need not be a hosting choice
ClojureScript, ReScript and TypeScript compile to JavaScript rather than requiring
a separate production VM. Their interop/bindings expose =fetch=, streams and other
host APIs: choosing a language need not mean abandoning JavaScript's runtime ecosystem.

ClojureScript's data structures or ReScript's types do not change the
=Request=/=Response= boundary. Compatible output can target browsers, servers or
durable hosts. This is interface portability, not a guarantee that every bundle
runs unchanged: emitted JS, modules and dependencies must fit the host. DOM-only
code and Node-specific libraries remain platform constraints.

*** FastTwitch: ClojureScript maps, native Fetch
FastTwitch expresses HTTP applications as Ring-style request/response maps and
ordinary handler functions and middleware. Its adapters bridge those maps to
native =Request=/=Response= objects; its clients use native =fetch=, body streams
and request options. Node HTTP, =Deno.serve= and =Bun.serve= differ underneath,
but the application-facing handler contract stays consistent.

*The practical benefit:* reuse routing, authentication and application logic when
changing runtimes instead of rebuilding the HTTP boundary. Runtime-specific
features still require matching adapters and tests. ReScript can bind to the same
Web APIs; FastTwitch is the ClojureScript example, not a requirement for other languages.

The GitHub hello-world/native-HTTP samples and the library's =serve= macro reduce
the server boundary to a Ring handler plus a runtime adapter.[fn:fasttwitch-examples]

#+begin_src clojure
(ns demo.http
  (:require [fast-twitch.routing :as routing]
            [fast-twitch.client.core :as client]
            [fast-twitch.macros :refer-macros [serve]]))

(defn hello [_request]
  {:status 200
   :headers {"Content-Type" "text/plain; charset=utf-8"}
   :body "Hello from ClojureScript"})

(def server
  (serve :handler (routing/ft-handler hello
                    {:protocol "HTTP/1.1" :remote-addr "127.0.0.1"})
         :hostname "127.0.0.1" :port 6464))

(-> (client/request! {:url "http://127.0.0.1:6464/"
                      :request-method :get :headers {}}
                     {:codec :text})
    (.then (fn [response] (println (:body response)))))
#+end_src

Here =serve= selects the native server adapter. =client/request!= converts the
request map to a native Fetch request and returns a response map; choosing
=:codec :text= consumes the body, while the default native codec preserves streams.

*** FastTwitch Celld: from HTTP handlers to named, stateful cells
Consider a chat application: give each room its own cell instead of coordinating
all rooms inside one server process. FastTwitch Celld adds ClojureScript cell
declarations, HTTP/RPC entry points, storage, alarms and WebSocket bindings.
HTTP still uses the Fetch model; the platform routes each room to its named cell,
and application code persists message history in that cell's SQLite/KV storage.

After eviction or restart, a new activation can reconstruct the room from that
stored history. An ordinary ClojureScript =atom= is not automatically durable;
neither is the call stack. This is Durable Objects-style state recovery, not
dquickts-style execution snapshots. The extension is not yet release-ready.

This short adaptation combines the GitHub direct-cell and storage examples.
It uses the extension's pinned compiler and build pipeline; configuration and
class-history files remain in the full examples.[fn:fasttwitch-cell-examples]

#+begin_src clojure
(ns demo.cells
  (:require [cljs.core :refer [await]]
            [fast-twitch.celld.context :as context]
            [fast-twitch.celld.storage.kv :as kv]
            [fast-twitch.celld.bindings :as bindings]
            [fast-twitch.celld.identity :as identity]
            [fast-twitch.celld.http :as http])
  (:require-macros [fast-twitch.celld.macros
                   :refer [deffetch defcell defworker]]))

(deffetch counter-fetch [ctx _request]
  (let [store (kv/native (context/storage ctx))
        n (inc (or (:value (kv/get-value store :n)) 0))]
    (kv/put! store :n n)
    {:status 200 :body (str n)}))

(defcell Counter {:binding :COUNTERS :include [counter-fetch]})

(deffetch ^:async worker-fetch [ctx request]
  (let [stub (identity/get-by-name
               (bindings/get-binding ctx :COUNTERS) "demo")]
    (await (http/forward! stub request))))

(defworker App {:include [worker-fetch]})
#+end_src

The Worker forwards a Fetch-shaped request to a named cell. The cell still returns
a ClojureScript response map, but its count is written to native durable KV—not
an =atom=. The bridge changes how code reaches the platform, not who provides durability.

*The through-line:* shared runtimes and Web APIs make this a common application
model, not a separate networking stack for every language or host. Workflow
journals preserve completed work, runtime snapshots preserve execution state,
and durable objects preserve an addressable unit's data and lifecycle. These are
different ways to let modern workloads survive beyond a single request or process.
